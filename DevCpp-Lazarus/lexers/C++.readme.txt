Econtrol .lcf 文件结构深度解析（基于你的真实文件）

一、文件本质

这不是 INI 文件，而是 Delphi/FPC 的 TWriter/TReader 组件持久化流。每一段都是一个有名字的对象集合：

object SyntAnal6: TLibSyntAnalyzer   ← 根对象
  Formats = < ... >                  ← 子对象集合 (TCollection)
  TokenRules = < ... >
  BlockRules = < ... >
  SubAnalyzers = < ... >
  TokenTypeNames.Strings = ( ... )   ← 字符串列表属性
  ...
end


尖括号 < ... > 内是 TCollection 的多个 item。

二、TokenTypeNames.Strings —— 全局类型注册表（基石）

定义了 18 种 Token 类型，按出现顺序从 0 开始编号：

索引 → 名称              索引 → 名称
 0 → 'Unknown'            9 → 'Symbol ::'
 1 → 'Comment'           10 → 'Symbol ()'
 2 → 'Identifier'        11 → 'Id modifier'
 3 → 'Symbol'            12 → 'Symbol ->'
 4 → 'String'            13 → 'Symbol ;'
 5 → 'Number'            14 → 'Goto label'
 6 → 'Preprocessor'      15 → 'Id after ~'
 7 → 'Id keyword'        16 → 'Id after ::~'
 8 → 'Symbol {}'         17 → 'Symbol :'


这个索引 N 就是后面所有引用的"主键"。 TokenRules 通过 TokenType = N 引用它，BlockRules 通过 TokenTypes = 2^N（位掩码）引用它。

三、Formats —— 视觉样式表

Formats 是 15 个样式 item，每个有 DisplayName（字符串键）+ 颜色/字体属性：

DisplayName    Font.Color    Font.Style    用途
─────────────────────────────────────────────────────
'Symbol'       clMaroon      [fsBold]      粗体棕红符号
'Number'       clNavy        [fsBold]      粗体深蓝数字
'String'       clTeal        []            青绿色字符串
'Identifier'   clBlack       []            黑色普通标识符
'Id keyword'   clBlack       [fsBold]      粗体黑（控制流关键字）
'Id type'      clPurple      []            紫色（类型名）
'Id special'   clOlive       []            橄榄绿（修饰符）
'Id templated' clNavy        []            深蓝（模板名）
'Comment'      clGray        [fsItalic]    灰色斜体注释
'Preprocessor' clGreen       []            绿色预处理指令
'Asm BG'       clWindowText  [] + BgColor  汇编背景色
'Label'        clRed         []            红色标签
'Operator XX'  clBlue        []            蓝色运算符
'Incorrect'    clBlack       [] + 红边框   错误标记


⚠️ 关键：Formats 与 TokenTypeNames 没有索引对应关系

Formats 的第 0 项是 'Symbol'，但 TokenTypeNames[0] 是 'Unknown'。两者通过字符串名称桥接，不是索引。

四、TokenRules —— 词法规则（三层桥接）

每个 item 有三个核心字段：
item
  StyleName = 'String'       ← ① 字符串 → 匹配 Formats.DisplayName
  TokenType = 4              ← ② 整数 → 匹配 TokenTypeNames 索引 4
  Expression = '"(...)"'     ← ③ 正则表达式
end


4.1 数据流图


源码文本 "hello"
    │
    ▼  Expression 正则匹配成功
    │
    ├── TokenType = 4 ──→ TokenTypeNames[4] = 'String' （语义分类）
    │
    └── StyleName = 'String' ──→ Formats['String'] = clTeal （视觉样式）
                                      │
                                      ▼
                               ATSynEdit 用 clTeal 绘制 "hello"


TokenType 和 StyleName 是两个独立维度：

字段 回答的问题 引用机制

TokenType = 4 "这是什么语义类型？" 整数索引 → TokenTypeNames[4]

StyleName = 'String' "它该什么颜色？" 字符串 → Formats.DisplayName

4.2 规则顺序 = 匹配优先级

文件中的 TokenRules 顺序（共 27 条）：

 0: String          → 普通字符串 "..."
 1: String raw      → C++11 原始字符串 R"(...)"
 2: String in define→ #include <header.h> 中的路径
 3: Id keyword      → catch/else/for/if/switch/while
 4: Label           → 行首标识符后跟 : (goto 标签)
 5: Label 2         → goto 后的标识符
 6: Char            → 字符字面量 'c'
 7: ~Id             → 析构函数名 ~ClassName
 8: ~Id after ::    → 类名::~析构函数
 9: Id keywords     → template 关键字
10: Id templated    → 模板名<TParam>
11: Operator XX     → operator 重载
12: Bad number suffix → 数字后非法后缀（红色边框标记）
13: Id              → 普通标识符（兜底）
14: Num hex float   → 0x1.Ap3 十六进制浮点
15: Num hex         → 0xFF / 0b1010
16: Num float       → 3.14 / .5e-2
17: Num decimal     → 42
18: Comment block   → /* ... */
19: Comment line    → // ...
20: Directive       → #define/#include/...
21: Symbol ;        → 分号
22: Symbol ->       → 箭头
23: Symbol { }      → 花括号
24: Symbol ::       → 作用域解析
25: Symbol :        → 冒号
26: Symbol ( )      → 圆括号
27: Symbol          → 其他符号 +-*/= <> [] , . ...


普通 Id 规则（第 13 条）排在关键字、数字、符号之后作为兜底——前面的规则都没匹配时才命中。

4.3 一个特殊案例：Bad number suffix

item
  DisplayName = 'Bad number suffix'
  StyleName = 'Incorrect'        ← 红色边框样式
  Expression = '(?<=[\d'#39'])[a-z_]\w*'
end


这条规则没有显式设置 TokenType（默认 0 = Unknown）。它的目的不是分类，而是视觉标记——把 42foo 中的 foo 用红色边框标出来。

五、BlockRules —— 代码块识别（状态机）

BlockRules 远比 TokenRules 复杂。它识别函数、类、结构体等代码结构，在代码树中展示、支持折叠。

5.1 两种 BlockType

类型 A：btTagDetect（标签检测，3 条规则）

不定义代码块边界，而是扫描特定关键字并赋予样式升级：
item
  StyleName = 'Id keyword'        ← 升级样式
  BlockType = btTagDetect
  ConditionList = <
    item
      TagList.Strings = (         ← 关键字列表
        '__asm' 'class' 'for' 'if' 'while'
        'template' 'namespace' ...
      )
      TokenTypes = 4              ← 2² → 只匹配 Identifier 类型的 Token
    end>
  TokenType = 7                   ← 升级为 'Id keyword' 语义
end


执行逻辑：
1. 词法分析器产生一个 Identifier（TokenType=2）Token
2. 检查其文本是否在 TagList 中
3. 如果在 → 将 TokenType 从 2(Identifier) 提升为 7(Id keyword)，应用黑色粗体样式

三个 btTagDetect 规则形成优先级链：

优先级最高 → 'id keywords'   → class/for/if/template/...  → 黑色粗体
           'id modifiers'  → const/static/virtual/...   → 橄榄绿
优先级最低 → 'id types'      → int/void/bool/string/...  → 紫色


类型 B：状态机型（识别函数/类/结构体定义，15 条规则）

5.4 多条 BlockRule 的"从具体到通用"降级链

文件对函数定义了 9 条规则，从最具体到最通用：

func :: :: :: with :   ← 三层命名空间 + 有 :/->/& 修饰
func :: :: ::           ← 三层命名空间
func :: :: with :       ← 两层命名空间 + 有 :/->/&
func :: ::              ← 两层命名空间
func :: with :          ← 一层命名空间 + 有 :/->/
func :: with &          ← 一层命名空间 + 有 &/&&/try
func ::                 ← 一层命名空间
func with :             ← 无命名空间 + 有 :/->/
func with &             ← 无命名空间 + 有 &/&&/try
func                     ← 最简函数（兜底）


每条规则用 CancelNextRules = True 确保最具体的匹配先命中，匹配成功后不再尝试后面的通用规则。

六、SubAnalyzers —— 嵌套语法切换

SubAnalyzers = <
item
  DisplayName = '__asm block'
  StyleName = 'Asm BG'                    ← 汇编块背景色
  StartExpression = '\b__?asm\x20*\{'    ← 匹配 "__asm {"
  EndExpression = '\}'                    ← 到 "}" 结束
  SyntAnalyzer = SyntAnal1               ← 切换到汇编分析器
end>


当遇到 __asm { 时，临时切换到 SyntAnal1（另一个 TLibSyntAnalyzer 实例，针对汇编语法），实现多语言嵌套高亮。

八、一句话总结核心关系

TokenTypeNames.Strings 是整个系统的"枚举定义"（索引 0-17）。TokenRules 通过 TokenType=N（整数）引用它来分类 Token，通过 StyleName（字符串）引用 Formats 来着色。BlockRules 通过 TokenTypes=2^N（位掩码）引用它来构建条件状态机，同样通过 StyleName 引用 Formats 着色。Formats 本身只认 DisplayName 字符串键——四个部分通过"索引 + 字符串名称"双重机制串联成一个完整的语法高亮引擎。
